The completion control, in place

Every rule below is the stylesheet progress.js injects, extracted from the source and reproduced byte-for-byte — the only change is renaming the #completionSlot scope so six instances can sit on one page.

Each panel puts the control on the real section ground with its real neighbour, .next-step-card, underneath it. That pairing is the whole point: the first version was a pale sage tint, and it read as a washed-out copy of the card below rather than as a separate thing.

Unset and done

The terracotta left bar identifies the component and never changes. The fill carries the state, and done is an inversion rather than another tint.

What to judge here. Is the unset state distinct enough from the sage card beneath it, and does the done state read as an achievement without shouting over the rest of the section? Those are the two questions the colour change was meant to answer.

When the write fails

The state is left exactly as it was and the failure is said plainly. Silently doing nothing is the one outcome that would make someone press it twice.

Guests see nothing at all

There is no fourth state, because the slot renders empty and collapses to zero height for anyone who is not signed in.

Why, given a button and a prompt would have been easy. Marking complete would do nothing even for the current session — this file keeps nothing whatsoever for a guest. And the end of a plan is the weakest moment to ask for a sign-up: a guest has no stored progress, so an account rescues nothing that was just read. The honest wording would have been “make an account, and note that none of what you just read was recorded.”

The site already asks, better and earlier — the existing “not being saved” notice fires at the first save that did not happen, while there is still a read ahead worth keeping. Asking twice is worse than asking once, and asking last is worse than asking first.
